# 01 — งานวิจัยและผลิตภัณฑ์ที่มีอยู่

## 1. ข้อจำกัดของอุปกรณ์ที่ต้องยอมรับก่อนออกแบบ

| ข้อจำกัด | ผลต่อการออกแบบ |
| --- | --- |
| แกนอนาล็อกมีความละเอียดจำกัด + deadzone ~0.1–0.2 | ต้องมี threshold/hysteresis ของเราเอง ไม่พึ่งค่า OS |
| นิ้วโป้งแม่นน้อยกว่านิ้วมือ ~3–5 เท่า | อย่าให้ต้องเล็งตำแหน่งต่อเนื่อง — ให้เลือกจาก "ช่อง" ที่มีขอบเขตชัด |
| ทิศ 8 ทางห่างกัน 45° | ต้องมี sector + hysteresis กันสั่นตรงเส้นแบ่ง |
| นิ้วโป้งเมื่อยเมื่อต้องค้างน้ำหนัก | งานส่วนใหญ่ควรจบใน < 500 ms, มี auto-repeat |
| จอยบางตัวมี drift | ต้อง re-center calibration ตอนต่ออุปกรณ์ |
| เกมที่ใช้ Raw Input / anti-cheat | การส่งคีย์ต้องเป็น SendInput ปกติ ไม่ใช้ driver/hook ลึก |

## 2. เทคนิคที่มีอยู่แล้ว และตัวเลขที่วัดได้จริง

| เทคนิค | หลักการ | ผลลัพธ์ที่รายงาน | บทเรียน |
| --- | --- | --- | --- |
| On-screen selection keyboard | เลื่อนเคอร์เซอร์ไปเลือกทีละตัว | ~5.6 WPM (เริ่มต้น) → 12.9 WPM (session 20) | ฐานที่ต้องชนะ |
| **TwoStick** (Költringer et al., GI 2007) | สองแกนลากผ่านกลุ่มตัวอักษร (ต่อยอด Quikwriting) | 4.3 → **13–14.9 WPM** หลัง 20 session, error 0.86% | สองแกนเร็วกว่า selection keyboard แต่ต้องฝึกนาน |
| **Daisywheel** (Steam Controller) | วงล้อ 8 กลีบ กลีบละ ~8–10 ตัวอักษร, LS เลือกกลีบ, RS เลือกตัว | ผู้ใช้รายงาน ~20–30 WPM (ยังไม่มีงานวิจัยควบคุมชัดเจน) | ตัวอักษรที่พบบ่อยอยู่ใกล้จุดพักนิ้ว = เร็วกว่าเรียงตามตัวอักษร |
| Quad-stick / bimanual (Sandnes & Aubert) | แบ่งคีย์บอร์ดซ้าย/ขวาให้สองแกน | เร็วกว่าแบบแกนเดียวชัดเจน | ความคุ้นเคยเชิงพื้นที่ของ QWERTY ช่วยลดการเรียนรู้ |
| One-stroke / stroke-based | ลากเส้นต่อเนื่องไม่ต้องยืนยัน | ~30 ตัวอักษร/นาที ใน 5 นาทีแรก | เรียนเร็วแต่เพดานต่ำ |
| Joystick + word prediction | ทำนายคำเพื่อลดจำนวนการเลือก | ~6 WPM (ผู้ใช้กล้ามเนื้ออ่อนแรง) | prediction สำคัญมากเมื่อความเร็วต่ำ |
| Flick / gesture (มือถือ) | ปัดสั้นๆ แทนการเลือก | เร็ว แต่ต้องมีหน้าจอป้อนกลับ | ต้องมี HUD |

> ตัวเลขทั้งหมดเป็น "ค่าที่รายงานในงานต้นทาง" ไม่ใช่ผลทดสอบของเรา —
> ต้องวัดซ้ำกับ build ของเราเองด้วย harness ใน [[02-roadmap-and-smoke-tests]]

## 3. บทเรียนที่ยอมรับเข้าแบบ

1. **Direct selection ชนะ scrolling** — 8×8 ที่เลือกได้ใน 2 การเคลื่อนไหว เร็วกว่าการไล่เมนู
2. **ความคุ้นเคยเชิงพื้นที่ช่วยจริง** — ถ้าตำแหน่งตัวอักษรสะท้อนอะไรที่ผู้ใช้รู้อยู่แล้ว
   (ความถี่, กลุ่มเสียง, แถวคีย์บอร์ด) การเรียนรู้เร็วขึ้นชัด
3. **ปล่อยเพื่อยืนยัน (release-to-confirm)** ลด misclick และเปิดทาง "ย้อนกลับ" ก่อน commit
4. **HUD จำเป็นในช่วงเรียนรู้** — daisywheel ทั้งหมดพึ่งวงล้อบนจอ; เราต้องมี overlay
   ที่โชว์ 8 กลุ่ม + ตัวที่เลือก เพื่อให้ตากับนิ้วตรงกัน
5. **ตัวอักษรที่ใช้บ่อยต้องอยู่ใกล้จุดพัก** — ทิศ ↑ ถูกที่สุด, ↖/↘ แพงที่สุด (นิ้วโป้งออกแรงเฉียง)
6. **Prediction คือตัวคูณ** — ภาษาไทยได้เปรียบเพราะไม่มีช่องว่างระหว่างคำ (ตัดคำได้จากพจนานุกรม)
7. **เพดานความจริง** — งานวิจัยจอยให้ ~15 WPM; เราได้ 64 ช่องแบบตรง + ปุ่มหน้าสำหรับ space
   จึงตั้งเป้า 20 WPM (EN) / 12 WPM (TH) ซึ่งเป็นเป้าที่ท้าทายแต่ไม่เพ้อฝัน

## 4. ทางเลือกที่พิจารณาแล้วไม่เลือก (พร้อมเหตุผล)

| ทางเลือก | ทำไมไม่เลือก |
| --- | --- |
| Chorded keyboard (1 ปุ่มผสมหลายปุ่ม) | เพดานเร็วสูง แต่ต้องท่องจำมหาศาล ผิดเป้า "ใช้งานลื่นไหล" |
| แป้นพิมพ์บนจอ (ซอฟต์แวร์ OS) | ช้า (~5–13 WPM) และบังหน้าจอ |
| Dictation / เสียง | คนละโจทย์, ต้องต่อเน็ต, พิมพ์ในที่เงียบไม่ได้ |
| Radial menu 16 ช่องต่อกลุ่ม | นิ้วโป้งแยก 16 ทิศไม่ไหว (±11.25°) |
| 4 ทิศ × 16 ช่อง | น่าสนใจเป็น Variant B (ดู [[01-open-questions]]) — เบากว่า แต่เลือกช้าลง |

## 5. สิ่งที่ยังไม่มีใครทำดี (โอกาสของ RniType)

- ผสาน **พิมพ์ + เมาส์ + คีย์ลัด** ในจอยตัวเดียว โดยไม่ต้องสลับแอป
- **ภาษาไทย**: ยังไม่มี scheme เกมแพดที่ออกแบบจากความถี่ตัวอักษรไทยจริง
- **สองภาษาในเครื่องเดียว** สลับด้วย D-pad โดยไม่ต้องเปลี่ยน layout ของ Windows
- หน้าตั้งค่าแบบ Logi Options+ (per-app profile, ดูชนิดจอยที่ต่ออยู่)
